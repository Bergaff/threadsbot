# Руководство: cookies аккаунтов Threads (JSON) — перенос, самодиагностика, защита от бана

Для админа Cloudflare-бота. Пошагово:
1. Что лежит в JSON и какие бывают форматы.
2. Как безопасно переносить аккаунты между ботами.
3. Правила, чтобы аккаунты не банили.
4. Как работает самодиагностика JSON в боте (и когда сработает алерт).
5. Google Colab поячеечно: массовая загрузка, проверка, SQL, пуш в D1, экспорт обратно.
6. Как менять код на GitHub **без мержа** в `main`.
7. Что исправлено, чтобы сценарий «пишу имя профиля → получаю текст или фото» заработал.

---

## 1. Формат JSON

`accounts/<имя>.json` — экспорт cookies сессии Threads. Это не просто данные,
это ключи доступа к аккаунту. Обращаться с ними как с паролями.

| Формат               | Где взять                         | Поле срока жизни    |
|----------------------|-----------------------------------|---------------------|
| Cookie-Editor        | «Export» в расширении браузера    | `expirationDate` (сек) |
| Playwright / EditThisCookie | `context.cookies()` / экспорт | `expires` (сек)     |
| Обёртка `{ cookies: [...] }` | некоторые экспортеры         | любое из двух       |

Бот принимает все три варианта и нормализует `sameSite` / `expires`.

**Ключевые cookies:** `sessionid` (обязателен), `ds_user_id`, `ig_did`.
Без `sessionid` сессия не рабочая. Остальные два дают предупреждение.

При применении в браузере cookies с доменов `.instagram.com` / `.threads.net` /
`.threads.com` **дублируются на оба Threads-домена**. Иначе сессия, снятая
с `threads.net` или Instagram, не доезжает до `www.threads.com`.

## 2. Перенос аккаунтов между ботами

> **Правило №1**: одна сессия = один IP в один момент времени.
> Если JSON одновременно используется на двух ботах / устройствах, Threads видит
> два разных IP на одной сессии и с высокой вероятностью пометит её как подозрительную
> (частая причина «тихого» бана без разлогина, но с урезанием API).

### Через бота (рекомендуется)
1. В старом боте: `/account_export имя` → получаешь `имя.json`.
2. В старом боте: `/account_del имя` → удаляем сессию, чтобы старый бот её больше не трогал.
3. В новом боте: пришли этот JSON файлом. Подпись к файлу = имя аккаунта
   (если файла `cookies.json`, подпиши `acc1`).
4. Проверь: `/accounts` и `/account_check`.

### Через скрипт (массово)
```bash
npm run accounts:import -- accounts --remote
```
Проверяет JSON, нормализует, upsert в D1. `--local` — локальная БД.

### Через Colab (без своей машины)
См. `notebooks/accounts_toolbox.ipynb` — ячейки: загрузка → проверка → SQL →
опциональный пуш в D1 по API → ZIP-экспорт → очистка.

### Что нельзя делать
- Коммитить `accounts/` в git (уже в `.gitignore`).
- Пересылать JSON в переписке — только личные файлы боту.
- Держать один и тот же аккаунт залогиненным в двух местах одновременно.

## 3. Как не банить

1. **Одна сессия = один IP**. См. выше.
2. **Лимит 20 запросов/час на аккаунт** (`LIMITS.accountHourly`). Бот сам ротирует.
3. **Свежие cookies**: после каждого успешного запроса бот вытаскивает актуальные
   cookies из контекста браузера и перезаписывает их в D1 (`markSuccess` в `threads.ts`).
   Это продлевает жизнь сессии.
4. **Мёртвые сессии** (редирект на `/login`) сразу помечаются `is_alive=0` и
   отдыхают до следующего экспорта.
5. **Не логинься в тот же аккаунт с телефона**, пока он крутится в боте.
6. **Cloudflare Browser Rendering ходит с чужого IP** (Cloudflare edge, не твоего).
   Не используй тот же аккаунт со своего IP параллельно — Threads увидит два IP.
7. Аккаунт не должен быть новым — свежие регистрации без активности банят быстрее.
   Прогони его 1–2 дня как человек (посты, лайки, реплаи) перед добавлением в бот.
8. Не гоняй `/account_check` через браузер на всех аккаунтах подряд — cron только
   читает JSON, не открывает Threads. Живой probe (`🧪 Test`) жжёт Browser Run.

## 4. Самодиагностика JSON

Каждые 6 часов (cron `0 */6 * * *` в `wrangler.toml`) бот:
- перебирает все аккаунты;
- для каждого вызывает `diagnoseAccountCookies` из `src/cookies.ts`;
- если проблемы есть — шлёт админам алерт.

Что проверяется:

| Функция                    | Что делает                                             |
|----------------------------|--------------------------------------------------------|
| `validateCookiesJson`      | JSON — массив (или `{cookies:[]}`) с `name`/`value`?  |
| `missingKeyCookies`        | Есть ли `sessionid`, `ds_user_id`, `ig_did`?           |
| `earliestCookieExpiry`     | Секунды и миллисекунды, самая ранняя дата              |
| `normalizeCookiesJson`     | sameSite / expires / domain по умолчанию               |
| `diagnoseAccountCookies`   | Собирает замечания в `issues`                          |

Порог «скоро истекает» — `LIMITS.cookieWarnDays = 7` дней.
Вручную: `/account_check`.

После успешного чтения профиля cookies **сами обновляются** в D1 из
`context.cookies()`. Отдельно «обновлять JSON руками» нужно только когда
сессия мертва (`/login`) или диагностика говорит «истекли».

## 6. Как менять код на GitHub, но НЕ мержить в `main`

Arena (и этот бот) работает в ветке сессии, например
`arena/01a020b8-threadsbot`. Каждый коммит уходит **только в эту ветку**.
Pull Request в `main` — это предложение, а не применение.

### Что происходит
1. Код коммитится в рабочую ветку.
2. Открывается PR: `arena/...` → `main`.
3. `main` **не меняется**, пока ты сам не нажмёшь зелёную кнопку **Merge**.
4. Можно смотреть diff, оставлять комментарии, просить правки, закрыть PR.

### Как смотреть, не мержа
- На GitHub: вкладка **Pull requests** → открыть PR → Files changed.
- Локально, не трогая `main`:
  ```bash
  git fetch origin
  git checkout arena/01a020b8-threadsbot
  # смотришь файлы, тестируешь
  git checkout main   # вернуться. main как был, так и остался
  ```
- Deploy с ветки (без мержа в main), если хочешь проверить на Worker:
  ```bash
  git checkout arena/01a020b8-threadsbot
  npx wrangler deploy
  ```
  Это выкатывает **содержимое текущей ветки**. `main` в репозитории при этом
  не меняется.

### Чего не делать, если не хочешь мержить
- Не нажимать **Merge pull request**.
- Не делать `git merge arena/...` пока ты на `main`.
- Не включать auto-merge.

Закрыть PR без мержа: на странице PR → **Close pull request**.
Ветка и коммиты останутся, просто предложение в `main` снимется.

## 7. Что исправлено в этом релизе

1. **Сессия Threads наконец ставится как в рабочей Python-версии.**
   Браузер сначала открывает `BASE_URL`, потом `addCookies`, потом `reload`.
   Cookies с `.instagram.com` / `.threads.net` зеркалятся на `.threads.com`.
   Раньше cookies добавлялись в пустой context — профиль открывался как гость,
   и основной сценарий «имя → посты» молча не работал.

2. **Загрузка JSON.** Файл нормализуется, можно подписать имя аккаунта,
   диагностика сразу после сохранения. `/account_del` / `/account_export` без изменений.

3. **Команды отвечают быстрее.** `sendChatAction(typing)` сразу, ответ
   `/start` `/help` `/language` уходит до очистки старых кнопок, D1-запросы
   для username идут параллельно. Telegram по-прежнему получает `200` через
   `ctx.waitUntil` (не ждёт хвост обработки).

4. **Username из ссылки.** `zuck`, `@zuck`, `https://www.threads.com/@zuck`
   и `https://www.threads.net/@zuck/post/...` — всё одно и то же.

5. **Самодиагностика** вынесена в `src/cookies.ts` (без Playwright), покрыта тестами.
   Умеет `{cookies:[]}`, секунды/миллисекунды, просроченные cookies отбрасываются
   перед `addCookies` (один протухший трекер больше не валит всю сессию).

Python-файлы (`bot.py`, `threads_check.py`) не трогались.

## Чек-лист после деплоя

1. `npm run deploy` — успех. Для Browser Rendering нужен **Workers Paid**.
2. Прислать JSON боту → «✅ имя — cookies сохранены в D1».
3. `/accounts` → аккаунт в списке 🟢.
4. Написать боту `zuck` → кнопки «📝 Текст» / «🖼 Скрины».
5. «Текст» → 5 постов + «Ещё». Это уже Queue + браузер (нужен Paid).
6. `Reply → 1` на пост → комментарии.
7. `/account_check` → список ok / замечаний.
